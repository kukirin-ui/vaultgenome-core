# Supply chain security — buyer-facing summary

| Last updated | 2026-05-06 |
|--------------|------------|
| Owner        | Founders + future security engineering hire |
| Audience     | Enterprise buyers' GRC / supply-chain teams, regulators |

This document describes the controls Vault Genome implements to give
buyers a short, verifiable answer to "did the binary you handed us
come from the source code you say it did, and has nothing been
tampered with along the way?"

The answer is "yes" and is independently verifiable using only public
infrastructure (sigstore Rekor transparency log, AWS Nitro Enclaves
PCA, GitHub Actions artifact attestations) — no Vault Genome
infrastructure or signing keys are trusted parties.

## What ships with every release

For each binary (`sagvd`, `acp-compute`, `acpctl`):

| Asset                         | Format       | Source           | Verification path |
|-------------------------------|--------------|------------------|--------------------|
| `<binary>`                    | Linux ELF    | reproducible Go build | rebuild from source |
| `<binary>.sig`                | Sigstore sig | cosign keyless | `cosign verify-blob` |
| `<binary>.cert`               | x509 cert    | sigstore Fulcio | embedded in `verify-blob` |
| `<binary>.sbom.spdx.json`     | SPDX 2.3 JSON| syft DIR scan   | parse + cross-check go.mod |
| `<binary>.sbom.sig`           | Sigstore sig | cosign keyless | same as `.sig` |
| SLSA provenance (`*.intoto.jsonl`) | in-toto v1.0 | slsa-github-generator | SLSA verifier CLI |

All artifacts are attached to the GitHub Release for the corresponding
signed semver tag (`v*.*.*`). Each release tag is itself git-signed by
a key whose fingerprint is in the
[CODEOWNERS](../../.github/CODEOWNERS) file's signing-key roster.

The combination of "byte-reproducible builds" + "build provenance
generated by a separate hardened workflow" + "provenance signed via
sigstore keyless" is the load-bearing trio for SLSA L3.

## Reproducibility — what it means in practice

Two builds from the same git commit on the same Go toolchain version
produce **byte-identical** binaries. This is enforced in CI by
`make verify-reproducible` which:

1. Builds every binary with `-trimpath` + `-buildid=` + `-s -w` flags.
2. Saves the resulting bytes.
3. Wipes the `bin/` directory.
4. Builds every binary again.
5. Diffs the bytes; any difference fails the build.

This means a buyer's auditor can:

```bash
git checkout v1.2.3
docker run --rm -v "$PWD":/src -w /src golang:1.27.2 \
  make build
sha256sum bin/sagvd
```

…and compare the SHA-256 against the one in the released
`provenance.intoto.jsonl`. Match = the binary the buyer received was
produced by the source code we published. No third-party trust needed.

## Cosign keyless verification — exact commands

Verifying a downloaded binary requires only the `cosign` CLI and a
network connection to the sigstore Rekor transparency log. No Vault
Genome key material needs to be trusted:

```bash
# 1. Download the binary, signature, and certificate
curl -L -O https://github.com/vault-genome/vaultgenome-core/releases/download/v1.2.3/sagvd
curl -L -O https://github.com/vault-genome/vaultgenome-core/releases/download/v1.2.3/sagvd.sig
curl -L -O https://github.com/vault-genome/vaultgenome-core/releases/download/v1.2.3/sagvd.cert

# 2. Verify signature + transparency-log entry
cosign verify-blob \
  --signature sagvd.sig \
  --certificate sagvd.cert \
  --certificate-identity-regexp 'https://github\.com/vault-genome/vaultgenome-core/\.github/workflows/release\.yml@refs/tags/v.*' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  sagvd
```

A successful exit means:

- The binary was signed by a Fulcio-issued certificate during a GitHub
  Actions run on the `release.yml` workflow at the named tag (i.e.,
  not on a fork, not on a PR, not on `main`).
- The signature is logged in Rekor — the operation is publicly
  auditable; an attacker who later compromised our keys (none exist;
  cosign keyless uses ephemeral certs) could not retroactively forge
  history.
- Anyone who downloaded the same release can independently confirm
  byte equivalence.

## SBOM — what's in a binary

`syft` produces an SPDX-2.3-format SBOM listing every Go module
included in the binary. For Vault Genome the SBOM lists, in addition
to standard-library packages:

- Direct dependencies (per `go.mod`):
  - `github.com/stretchr/testify` (test-only — SBOM marks it
    accordingly)
  - `go.etcd.io/bbolt` (audit log persistence)
- Indirect dependencies — currently 4 transitive packages, every one
  with a justification file under
  [`docs/dependencies/`](../dependencies/).

The SBOM is signed alongside the binary; integrity is end-to-end.
Buyers can ingest the SBOM into their SCA tooling (Snyk, Veracode,
Phylum) for ongoing vulnerability monitoring without re-scanning the
binary.

## Vulnerability scanning at build time

Every `vault-gate` CI run executes:

| Check          | Tool                  | What it catches |
|----------------|-----------------------|------------------|
| `govulncheck`  | golang.org/x/vuln     | Known CVEs against actually-reachable code paths |
| `osv-scanner`  | google/osv-scanner    | Known CVEs against go.mod (broader, less false-positive-suppressed) |
| `gitleaks`     | gitleaks/gitleaks-action | Hard-coded secrets in commits |
| `golangci-lint`| golangci.com/lint/v6 | gosec, errcheck, ineffassign, … |
| `dep-allowlist`| `scripts/check_dep_allowlist.sh` | Direct deps off the approved list |
| `dep-depth`    | `scripts/check_dep_depth.sh` | Transitive chain length > 3 hops |

A PR that breaks any sub-check cannot merge; the merge gate is
documented in [docs/doctrine/ci-security-policy.md] (private repo).

## Buyer evaluation FAQ

**Q: Can you produce evidence the binary I'm running was built from
the source you publish?**
A: Yes. `cosign verify-blob` against the binary, sig, and cert from
the release. The cert chains to GitHub Actions via Fulcio, the
signature is logged in Rekor, and the build provenance attestation
identifies the exact git commit + workflow run. SLSA L3 today; L4
moves to a hermetic builder when funded.

**Q: How do I know nothing was added in the release pipeline that
wasn't in the source?**
A: Reproducible build flag set means you can rebuild the binary from
source on your own infrastructure and confirm byte equivalence (SHA-256
match against the released artifact). If they differ, our CI is
compromised — please contact ops@vaultgenome.com immediately.

**Q: What's your SBOM update cadence?**
A: SBOMs are regenerated on every release tag. Between releases the
production binary's SBOM is the same as the release one — there is no
hot-patching path that could insert new dependencies. CVE monitoring
between releases is the buyer's responsibility against the SBOM
already shipped.

**Q: Have you been audited?**
A: Not yet — the codebase is audit-ready (SOC 2 controls in place,
ISO 27001-aligned, code under doctrinal CI gates) but no formal
audit has been engaged. See
[`docs/compliance/crosswalk.md`](../compliance/crosswalk.md) for the
controls-to-frameworks map and 2027 timeline.

**Q: Who owns the signing key?**
A: No one. Cosign keyless uses ephemeral certificates issued by
Fulcio for the duration of a single CI run; the private key never
leaves the GitHub Actions runner's memory and is not persistable.
This intentionally rules out the "compromise the signing key, sign a
malicious binary" attack class — there is no key to compromise.
